## Findings from the adversarial pass (none blocking; N-1..N-3 are required corrections for 05)

### N-1 (required) — §4.17 last paragraph, §5.2 `geekonomy-deployer@`, R-16, §12: `roles/container.developer` cannot be "restricted in-cluster by a namespace RoleBinding"

GKE authorizes a request if **either** IAM **or** Kubernetes RBAC allows it. `roles/container.developer` is a project-level IAM role that grants `container.*` permissions on API objects (pods, deployments, secrets, …) in **every namespace of every cluster in the project**. Granting it to `geekonomy-deployer@` therefore gives the foreign repo's workflow write access to `kradle`, `atlas` and the platform namespaces regardless of the `RoleBinding`; the RoleBinding adds nothing. R-16's mitigation ("one AR repo + one namespace RoleBinding") is void as written, and the §12 acceptance test ("`geekonomy-deployer@` must be denied outside `geekonomy`") would fail.

Correction (three lines): give `geekonomy-deployer@` **`roles/container.clusterViewer`** (only `container.clusters.get`, which is what `get-gke-credentials` needs) instead of `roles/container.developer`, and keep the namespace `RoleBinding` (`edit` in `geekonomy`) as the *only* grant of object access — then IAM allows nothing inside the cluster and RBAC bounds the SA to one namespace. Apply the same pattern to `bpx` (askExpertQuestion) if D-9 keeps it. `github-deployer@` may keep `roles/container.developer` because it is intended to deploy cluster-wide (the `crd-admin` ClusterRoleBinding is still needed — CRD create is not in `container.developer` — so that part is correct). Update §5.2, §4.17, R-16 and the §12 can-i matrix accordingly.

### N-2 (required) — §5.2 "apply only from `attribute.ref == "refs/heads/main"`": not expressible with the mapping in §5.1

A `principalSet://…/attribute.<name>/<value>` binding keys on **one** mapped attribute. With `attribute.repository` and `attribute.ref` mapped separately, "repository X **and** ref main" cannot be bound: binding on `attribute.repository/<repo>` allows every branch of that repo, and binding on `attribute.ref/refs/heads/main` allows the `main` branch of *every* repo the provider admits. Two correct forms — pick one and write it into §5.1/§5.2: (a) bind the apply SAs (`github-terraform@`, `geekonomy-deployer@` for its terraform apply) with the exact subject, `principal://iam.googleapis.com/projects/<num>/locations/global/workloadIdentityPools/github/subject/repo:<owner>/<repo>:ref:refs/heads/main` (GitHub's `sub` claim for a branch push; `google.subject = assertion.sub` is already mapped), and the plan/PR SAs with `principalSet://…/attribute.repository/<repo>`; or (b) add a composite mapping `attribute.repository_ref = assertion.repository + ":" + assertion.ref` and bind on it. Note GitHub `sub` for `pull_request` events is `repo:<owner>/<repo>:pull_request`, which is why the plan SA must use the repository attribute, not the subject.

### N-3 (required) — §2 #25, §4.12, §12: the trial-telemetry verification must decompress before hashing

`data/trial-evidence/README.md:46-58` states the container holds **179 `*.ndjson.zst` + `BULK-MANIFEST.tsv` (100.7 MB stored)** and that `BULK-MANIFEST.tsv` checksums are over the **uncompressed originals** (7.77 GB); the README's own restore recipe is `zstd -dq` then `sha256sum`. The document says the copy is "verified against the repo's committed `BULK-MANIFEST.tsv` checksums" and §8 sizes the archive with "7.77 GB" in mind. Write the mechanics explicitly so 06 does not hash the `.zst` objects: after the transfer, for each manifest row `gcloud storage cat gs://…/trial-telemetry/<path>.zst | zstd -d | sha256sum` must equal column 1 (a one-line script in the plan; also the stored size is ≈ 100 MB, not 7.77 GB — correct the size in §2 #25/§8 so the cost row and the transfer-time estimate are right). The repo pointer change (§11) should include the `gcloud storage cat … | zstd -d` form of the README's `az storage blob download` example.

### N-4 (consistency) — §5.2 `bpx-runtime@` `roles/cloudsql.client` vs §4.7 "no Auth Proxy sidecar required"

`roles/cloudsql.client` is only needed by the Cloud SQL Auth Proxy / connector; §4.7 connects over private IP with `sslmode=require`, so either drop the SA row (no GCP role is needed for a private-IP connection) or state that bpx uses the proxy. Same reasoning already makes geekonomy's runtime correctly have no SA in §5.2 — make bpx match.

### N-5 (tooling note) — §7 `gavinbunney/kubectl`

That provider's last release is 1.14.0 (2022) and it is unmaintained; the maintained fork `alekc/kubectl` exposes the same `kubectl_manifest` resource. Name the fork (or pin the version knowingly) in §7 so the `addons` stage does not start on an abandoned provider.

### N-6 (wording) — §4.13 last sentence, R-19: "fallback"

In this repo's vocabulary a fallback is a silent degradation; this one is an *explicit alternative selected by a Phase B result*, which is fine — say "alternative chosen if A8 fails, recorded in 03 §3.1" so nobody reads it as an automatic branch. Also fold into A8: if the `firebase-tools` dry run fails on **permissions** rather than on ADC, add only the minimal role the error names (Firebase Hosting Admin is sometimes not sufficient for the CLI's project/API-enablement probes) — never `roles/firebase.admin`, never a key.

### N-7 (nit) — §4.18 "99 kinds in `packages/kradle/charts/crds/`"
