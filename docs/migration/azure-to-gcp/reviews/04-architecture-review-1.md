### F-4 (checklist item 4) — stateful data: three gaps and one non-implementable mechanism

- (a) **`hub-development/hub-redis-pvc` (10 Gi Premium disk)** appears nowhere in §2 #11, §4.6 or §4.12. State "cache only, not exported" explicitly (as §4.6 does for a5c-app's redis) so the decommission checklist is complete.
- (b) **PD snapshots (§4.5, §4.12 cost row)**: "`google_compute_resource_policy` daily snapshot … attached by the PD CSI `VolumeSnapshotClass` or by node-label policy" is not a mechanism. A resource policy (snapshot schedule) attaches to a *named* disk via `google_compute_disk_resource_policy_attachment`; the CSI-provisioned PD name is only known after the PVC binds, so terraform cannot declare it, and a `VolumeSnapshotClass` produces one-off `VolumeSnapshot` objects, not a schedule. Pick one and write it down: **(recommended)** a source-controlled `CronJob` in `packages/atlas/webui/deploy/base/backup-cronjob.yaml` running `pg_dump -Fc` to `gs://boot-464019-pg-dumps/<ns>/<date>.dump` via Workload Identity (`roles/storage.objectCreator` on that bucket) — it reuses the bucket, the restore Job and the row-count verification the document already defines; or Backup for GKE (`google_gke_backup_backup_plan`, ≈ $1.5/GiB-month + per-pod fee). Apply the same choice to gitea's PVC (10 Gi ×2), which today is on `emptyDir` and will hold real state on GKE for the first time.
- (c) **kradle CR data export/import (§2 #1, D-16)**: name the git home of the export and import scripts (e.g. `packages/kradle/core/scripts/cr-export.mjs` / `cr-import.mjs`, with tests), the list of *durable kinds* (Org, User, Repository, … — enumerate; the CRD group has 99 kinds), and the validation step (each object re-validated against the CRD schema of the GKE release, `status` re-derived by the controller). A raw `kubectl get -o json` piped into `kubectl apply` is what the ground rules forbid; a scripted, validated import of business records is fine — the document must make the distinction explicit. Also fix the cross-reference: §2 #1 says "(D-15)" for the import; the decision is **D-16**.
- (d) **geekonomy PG + Redis** — see F-1.

### F-5 (checklist item 6, secrets) — §4.8: value provenance for Secret Manager is unstated

"Secret **values** are entered once by the owner with `gcloud secrets versions add`" — from where? GitHub Actions secrets are write-only and cannot be read back; the only other place the current values exist is inside the AKS `Secret` objects. Reading them out with `kubectl get secret -o json` on a workstation is a payload copy of secret material through an unmanaged path. **Add a "value source at migration" column** to the §4.8 table with one of three provenances per secret: **regenerate at the issuer** (GitHub OAuth apps for `atlas-*-github-oauth` / `kradle-*-github-oauth` — regenerate the client secret in the GitHub app settings and paste it once; vendor API keys likewise), **generate fresh** (`atlas-*-postgres`, `content-studio-postgres`, `bpx-postgres` — the restore creates the role, so the old password is irrelevant; `kradle-*-test-auth`), or **owner-executed one-time transfer** only for values that cannot be rotated (list them; expected: none). Note that regenerating the GitHub OAuth secrets invalidates the AKS deployment's copies at that moment — so it must happen *at* cutover, not before, or the AKS side must receive the new value too (which the "both paths coexist" rule of §5.4 requires; say which).

### F-8 (isolation) — §6: the shared `kradle-org-a5c-ai` namespace is not addressed

02 §1.2 and `publish.yml:2389-2423` document that both releases render the same `kradle-org-a5c-ai` namespace (`templates/org-namespace.yaml`, `helm.sh/resource-policy: keep`) and the deploy job re-stamps Helm ownership on every run so the other environment's `helm upgrade` stops erroring. §6 claims the layout "exactly mirrors today's" and R-3 covers only the CRDs. Carrying the re-stamp hack to GKE carries the prod/staging ownership fight with it. Decide: env-prefixed org namespaces (`kradle-org-<env>-<org>`), or the org namespace owned by exactly one release with the other env's chart rendering none (`org.namespace.create=false`), and add it to §11's chart changes. This is also where the "kradle → atlas in the **same** environment only" NetworkPolicy must be stated per org namespace, since dispatch Jobs there call back into the api.

### F-9 (IaC) — §7: one root for cluster + `kubernetes_manifest` addons does not plan on an empty project

`kubernetes_manifest` (ClusterIssuers, `ClusterSecretStore`) requires the target CRD to exist **at plan time**, and the `kubernetes`/`helm` providers need a reachable cluster endpoint that is unknown until the first apply — the documented `apply-gcp.yml` "plan on PR" will fail on day one and after any cluster recreate. Split `envs/gcp-boot` into two stages with separate state prefixes: `gcp-boot/platform` (APIs, VPC/NAT, GKE + pools, AR, IAM/WIF/SAs, buckets, Secret Manager shells, budget, alert policies) and `gcp-boot/addons` (helm releases, issuers, secret store, namespaces/quotas/network policies), the second reading the first via `terraform_remote_state`; or keep one root but use the `kubectl` provider (`kubectl_manifest`, which defers to apply) for CRD-backed objects and `depends_on` the cert-manager release. Also reconcile §4.1 ("control plane stays public… authorized networks") with §11 (add `master_authorized_networks_config`) — with hosted runners you either leave the authorized list disabled or you must add `0.0.0.0/0`, which is the same thing; say "disabled".

### F-10 (accuracy) — source-change index points at the wrong file for the org-namespace pull secret

§4.2 attributes the `acr-pull` copy into `kradle-org-*` to `agent-dispatch-controller.js` "copy logic". There is no such logic in `packages/kradle/core/src` (grep for `acr` / `imagePullSecret` returns nothing); the copy is rendered by the chart — `packages/kradle/charts/templates/assistant-org-secret.yaml:16` and `assistant-identity.yaml:19` iterate `.Values.global.imagePullSecrets`. Removing `global.imagePullSecrets` (already in §11) is sufficient; fix the citation so the implementing task does not hunt for controller code. Smaller items in the same category: `controller.service.loadBalancerIP` (§4.3) is deprecated in Kubernetes ≥ 1.24 — it still works on GKE today, but note the annotation `networking.gke.io/load-balancer-ip-addresses` as the supported form; R-2's "issue with `letsencrypt-staging` first on GKE to prove the HTTP-01 path" cannot precede DNS for the real hosts — use a canary host (`gke-canary.a5c.ai`, explicit A record to the new IP) in step 1 of §4.4 instead.

### F-11 (DNS precision, non-blocking) — §4.4

The mechanics are correct. Two rules to write down so an operator does not trip: (1) RFC 4592 closest-encloser — once an explicit `kradle-staging.a5c.ai` record exists, `gitea.kradle-staging.a5c.ai` no longer matches `*.a5c.ai`; the document adds both, but state it as a rule ("every host under a label that gets an explicit record needs its own explicit record") because step 2 (`kradle` + `gitea.kradle`) and `benchmarks` (Firebase A + TXT) depend on it; (2) at step 3 delete the explicit records only *after* confirming the wildcard change has propagated (`dig +short <random>.a5c.ai @ns41.domaincontrol.com`), otherwise a rollback of the wildcard would briefly leave the explicit hosts on GKE and everything else on Azure — which is acceptable but should be a conscious state.
