**Ground rules that bind every step** (from the run's instructions; repeated so nobody has to look them up):

1. **Source first.** Every artefact that reaches GCP is produced from its git origin — a workflow, a Helm chart, a terraform root, a manifest in a repo. No `az acr import`, no `kubectl get -o yaml | kubectl apply`, no copying of running manifests, no copying of TLS or other secrets out of AKS. **There is no non-dump data move:** kradle starts from the chart bootstrap on GKE (owner decision 2026-09-16); every other stateful item is a database dump or a bucket copy (Phase E).
2. **No fallbacks.** A failing command or missing access is a **blocker**: report the exact error and stop that lane. Never substitute a default.
3. **Azure is read-only** until Phase H, and Phase H starts only after the owner's decommission approval (breakpoint OB-3). Two stated exceptions: (a) **ephemeral pods** created in the AKS cluster with `kubectl run` for read-only dumps (E.0.4, E.0.6, X-E.8) are permitted and are deleted afterwards (`--rm`); Azure **control-plane** writes (firewall rules, scaling, secrets, role assignments) are not. No other Azure control-plane write exists before Phase H.
4. **Secret values are never written** into docs, task outputs, chat, git or CI logs. Secrets are named by Secret Manager name / GitHub secret name. Values enter GCP exactly once, typed or piped by the owner into `gcloud secrets versions add` (04 §4.8).
5. **Environments:** staging is always done before prod at every step that has both.
6. **Owner breakpoints (only three):** OB-1 plan approval (**before the docs commit and before any `terraform apply`** — it is the first thing that happens), OB-2 cutover (before Phase G step G.3 — the prod hosts), OB-3 decommission (before Phase H.2).       cluster_name: ${{ vars.GKE_CLUSTER_NAME }}

```bash
printf '%s' "$TA" | gcloud secrets versions add kradle-prod-test-auth    --data-file=-     # shell 2 — same value
unset TA
gcloud secrets versions access latest --secret kradle-staging-test-auth \
  | gh secret set KRADLE_TEST_AUTH_SECRET --repo a5c-ai/babysitter                         # GitHub repo secret, via stdin
```

## 5. Phase E — Data migration

**E.0 (wave 0) exports may start as soon as B.2's full `platform` apply has created `boot-464019-azure-archive` and `boot-464019-pg-dumps`** (X-B.15) — this is the only deviation from the literal phase order in §0, allowed because exports are read-only and R-1 says the AKS cluster may stop responding at any time. There is **no** `-target` apply of the buckets ahead of the cluster (removed 2026-09-16: B completes before any export). Every export is **read-only** on Azure, writes a manifest (`gcloud storage ls -L` + `SHA256SUMS`) and is verified before anything depends on it. Workstation tools: `az`, `kubectl` (AKS context `aks-hub-development-westus3-v2`), `gcloud storage`, `azcopy`, `pg_dump`/`pg_restore` 16, `zstd`, `sha256sum`. Nothing is deleted on Azure in this phase.

Conventions: `DATE=$(date -u +%Y%m%dT%H%M%SZ)`; every dump is `-Fc` (custom) unless the target is Cloud SQL (`-Fp | gzip`); every upload is followed by a **CRC32C** comparison — `gcloud storage hash --hex --skip-md5 <local file>` vs `gcloud storage hash --hex --skip-md5 gs://…/<obj>` → equal `crc32c_hash` (`gcloud storage hash` computes MD5 and CRC32C only; there is no `--sha256`, and MD5 is absent on parallel-composite uploads, so CRC32C is the check) — the local `sha256sum` sidecar `<obj>.sha256` stays the archival record and, for dumps of a few GB, may additionally be re-checked with `gcloud storage cat gs://…/<obj> | sha256sum`; every Postgres export records **per-table row counts before** (`SELECT relname, n_live_tup FROM pg_stat_user_tables ORDER BY 1` is an estimate — use `SELECT count(*)` per table via a generated script `raw/data/rowcount.sql`) into `raw/data/<item>-<DATE>.counts.tsv`.
